Дата: 2026-06-11 · Статус: проектирование (код не писать)
База: реализованный MVP v1.1 (`2026-06-11-renovation-estimator-mvp-design.md`).

## 1. Product Review: MVP глазами мастера по ремонту

Сильные стороны MVP: геометрия считается честно (проёмы, потолок), материалы —
целыми упаковками, цены снапшотятся, смету можно отдать клиенту ссылкой.

Критические пробелы с точки зрения практика:

1. **Три работы — это не цикл отделки.** Реальный малярный цикл во Франции
   (peinture sur murs intérieurs) — это 6–9 операций: обработка трещин,
   армирование, два вида шпаклёвки, шлифовка, грунтовка, акриловые швы,
   покраска в несколько слоёв. Смета из трёх строк выглядит непрофессионально
   и занижает реальную стоимость в 2–3 раза.
2. **«Шпаклёвка» без разделения старт/финиш** — это разные работы, разные
   материалы (dégrossissage ≈ 13 €/мешок vs finition ≈ 19 €/мешок), разные
   цены за м².
3. **Нет погонных метров.** Трещины, расшивка швов и акрил считаются в м.п.,
   а не в м² — текущая модель «всё × S_базовая» это не выражает.
4. **Нет штучных материалов.** Шлифовка расходует абразивные диски (шт.),
   акрил — картриджи (шт.); enum `l|kg` недостаточен.
5. **Смета — плоский список.** Профессиональный devis группируется по
   разделам (préparation → enduits → peinture); клиент и страховая это ожидают.
6. **TVA одной цифрой 20%.** Во Франции ремонт жилья старше 2 лет идёт по
   **TVA 10%** — для целевой аудитории это основной кейс, 20% — для нового
   жилья. Нужны пресеты.
7. Прочее, замеченное по ходу (не блокирует Phase 1.1): нет защиты/укрывки
   (bâchage), снятия обоев (dépose papier peint), покраски плинтусов и
   столярки (boiseries), выезда (déplacement), позиций «forfait»; потолок и
   стены красятся по одной цене, хотя потолок обычно дороже.

Пункты 1–6 решаются в Phase 1.1; пункт 7 — Phase 2 (см. §7).

## 5. Изменения модели данных и формул (проект, без кода)

БД (SQLite, `ALTER TABLE ADD COLUMN` при старте — Alembic не вводим):

- `work_types` + `group_code TEXT`, `sort_order INTEGER`,
  `quantity_basis TEXT CHECK(area|length) DEFAULT 'area'`,
  `max_layers INTEGER DEFAULT 3`, `active INTEGER DEFAULT 1`.
- `room_works` + `quantity REAL` — для `length`-работ хранит введённые м.п.;
  для `area`-работ NULL (количество = S_базовая, как раньше).
- `materials.consumption_per_m2` — колонку не переименовываем (SQLite),
  семантика расширяется до «расход на единицу работы»; в API/сиде поле
  называется `consumption_per_unit`.
- `consumption_unit` — допускаются `l | kg | u | m2`.

Формулы (дополнение §5 дизайн-дока MVP):

```
quantity = S_базовая                  если quantity_basis = area
quantity = введённые м.п.             если quantity_basis = length

labor_cost    = quantity × unit_price × layers
consumption   = quantity × consumption_per_unit × layers
packages      = ceil(consumption / package_size)
material_cost = packages × package_price
```

UI шага 2: работы рендерятся по группам в `sort_order`; для `length`-работ
вместо площади — поле «Длина, м.п.» (для `acrylic` префилл = периметр комнаты
P, для `crack_treatment` пусто — мастер вводит фактическую длину трещин).
Слои ограничены `max_layers`. Печать и share-view группируют строки по
разделам с подытогами; итог подписывается Total HT / TVA % / Total TTC,
селектор TVA — пресеты 10 % и 20 % (ручной ввод 0–30 остаётся).

API не меняет форму маршрутов; расширяются схемы: `GET /api/price-list`
отдаёт `groups`, `vat_presets` и новые поля работ; `rooms`-payload принимает
`quantity` для length-работ; ошибка `quantity` обязателен для length-работы —
код `quantity_required`.

## 6. Миграционный план MVP → Phase 1.1

Шаг 1. Данные: положить `price_list.seed.v2.json` как основной
`price_list.seed.json`; сид-загрузчик становится upsert-ом по `code`
(обновляет справочник, помечает `putty` как `active=0`, добавляет группы).

Шаг 2. Схема: стартовая «мини-миграция» — проверка отсутствующих колонок и
`ALTER TABLE ADD COLUMN` с дефолтами (идемпотентно). Существующие локальные БД
продолжают работать; старые сметы читаются как раньше (снапшоты).

Шаг 3. Backend: расчёт по `quantity_basis`, валидация `quantity` и
`max_layers`, расширенный `GET /api/price-list`. Тесты: length-работа,
штучный материал (диски: 45.86 м² × 0.04 шт/м² = 1.84 шт → ceil(1.84 / 25) =
1 коробка), TVA 10 %, группировка в ответе.

Шаг 4. Frontend: группы на шаге 2, поле длины, пресеты TVA, разделы и
подытоги в смете/печати/share-view.

Шаг 5. Закрыть долги MVP (входит в Phase 1.1): подключить загрузку фото на
шаге 1 к реализованному API; share-view — отдавать сохранённые расход/упаковки
из снапшотов вместо прочерков.

Шаг 6. Acceptance: комната 4 × 3 × 2.7 (контрольная), полный цикл из 8 работ,
трещины 6 м.п., акрил по периметру 14 м.п. — печать devis с тремя разделами,
TVA 10 %.

Откат: сид v1 остаётся в git-истории; новые колонки имеют дефолты, поэтому
старый код с новой БД не ломается.

## 7. Scope: что обязательно в Phase 1.1, что в Phase 2

### Phase 1.1 (обязательно)

1. Справочник из 8 работ с группами (сид v2, §3–4).
2. Единица м.п.: `quantity_basis = length`, ввод длины, префилл периметром для акрила.
3. Штучные материалы (`consumption_unit: u`) и материал в м² (стеклохолст).
4. Ограничение слоёв `max_layers` (покраска 1–3).
5. Группировка сметы по разделам + подытоги; итоги HT / TVA / TTC.
6. Пресеты TVA 10 % / 20 %.
7. Долги MVP: загрузка фото из UI, расход/упаковки в share-view.
8. Тесты на новые формулы и валидации.

### Phase 2 (переносится)

- Реквизиты devis: номер, дата, срок действия, SIRET, assurance décennale,
  mentions légales, поле клиента, «bon pour accord».
- Раздельные цены стены/потолок; покраска потолка как отдельная позиция.
- Доп. работы: dépose papier peint (снятие обоев), protection/bâchage
  (укрывка), peinture des boiseries/plinthes, déplacement, позиции «forfait».
- Правка норм расхода в форме; экран редактирования прайс-листа.
- Серверный PDF, Alembic, HEIC, markup_pct/status, AI-анализ фото, Excel,
  регистрация, мультивалютность (прежний список Phase 2/3 в `PROJECT.md`).
