# Codex — Требования к реализации MVP «Renovation Estimator»

Источник истины по дизайну: `docs/superpowers/specs/2026-06-11-renovation-estimator-mvp-design.md` (v1.1, scope урезан).
Этот документ — операционное ТЗ: что строить, в каком порядке, критерии приёмки.

## Статус реализации

По состоянию на 11 июня 2026 года реализованы backend-скелет, модуль расчёта,
REST API, фото API, React frontend, RU/FR и print-CSS. Backend pytest (17
тестов), frontend typecheck и production build проходят.

Известное отклонение: выбор фото на шаге 1 frontend валидируется, но пока не
отправляется в реализованный endpoint загрузки. Поэтому полный пользовательский
фото-сценарий остаётся незавершённой интеграцией, хотя API и его лимиты покрыты
тестами.

## 1. Стек и структура

- **Frontend**: React 19, Vite 7, TypeScript, react-router; i18n — словари ru/fr
  (react-i18next или аналог). Папка `frontend/`.
- **Backend**: Python 3.12+, FastAPI, SQLAlchemy 2.x, Pydantic v2. Папка `backend/`.
- **БД**: SQLite (`data/app.db`), схема — §6 дизайн-дока. Создание —
  `create_all` + сид из `data/price_list.seed.json` при первом запуске.
  **Без Alembic** в MVP.
- **Фото**: диск, `data/uploads/{estimate_id}/`, uuid-имена; в БД метаданные.
- **Печать**: только print-CSS на frontend. **Серверного PDF нет.**
- Тесты backend — в `tests/` (pytest).

## 2. Выполненный порядок работ

1. Скелет backend: модели, `create_all`, сид прайса.
2. Модуль расчёта (`backend/.../calculation.py`) — чистые функции, без I/O.
   TDD: сначала тесты из §5 ниже.
3. REST API по §7 дизайн-дока + OpenAPI-доки.
4. Frontend: 4 экрана + share-view (§2 дизайн-дока), print-CSS для сметы.
5. Acceptance-прогон сценария §3 дизайн-дока.

Пункты 1–4 в основном реализованы. Автоматические проверки включают backend
pytest и frontend typecheck/build. Полный браузерный acceptance не
автоматизирован; сквозная загрузка фото через UI остаётся ограничением,
указанным выше.

## 3. Жёсткие требования

- **Формулы только на backend.** Frontend показывает ответ
  `POST /api/estimates/{id}/calculate`, ничего не пересчитывает сам.
- **Снапшоты цен**: при добавлении работы в комнату цены и нормы копируются из
  справочника в `room_works`; справочник в MVP read-only (`GET /api/price-list`).
- **share_token**: `secrets.token_urlsafe(16)` минимум; по токену — только чтение.
- **Без авторизации**: никаких user-таблиц; «мои сметы» — id в localStorage.
- **Валидация на границе** (Pydantic): диапазоны из §4 дизайн-дока; фото
  jpeg/png/webp, ≤ 10 МБ, ≤ 10 шт. на смету; проверять MIME и magic bytes.
- **Ошибки**: конверт `{ "error": { "code", "message" } }`; коды стабильные,
  тексты локализует frontend.
- **i18n**: все строки UI в словарях ru/fr; имена работ из `name_ru`/`name_fr`.
- Конфиг — через `.env` (см. `.env.example`); ничего не зашивать в код.

## 4. Критерии приёмки и текущий результат

1. Сценарий: создать смету → фото → комната 4×3×2.7 с окном 1.5×1.4 и дверью
   0.9×2.05 → шпаклёвка(2)+грунтовка(1)+покраска(2) → расчёт совпадает с
   контрольным примером (S_базовая = 45.86 м²) → печать из браузера выглядит
   как смета → share-ссылка открывает read-only вид.
2. Правка цены работы в смете меняет итог; сид-прайс при этом не меняется.
3. Переключение RU/FR меняет весь UI и названия работ.
4. Все тесты зелёные: unit расчёта, API, лимиты фото.

Расчёт, снапшоты цен, RU/FR, print-CSS и read-only share-view реализованы в
коде; backend-тесты проходят. Фото upload/delete проверен на уровне API, но
UI-интеграция upload отсутствует. Share-view не вызывает `/calculate`, поэтому
расход и число упаковок в нём отображаются прочерками. Полный браузерный
acceptance остаётся ручной проверкой.

## 5. Обязательные unit-тесты расчёта

- Контрольный пример §5 дизайн-дока (точные числа).
- Проёмы больше площади стен → S_стен = 0 + warning в ответе.
- `include_ceiling = false` → потолок не считается.
- Округление: упаковки всегда `ceil`, деньги до 0.01 (HALF_UP).
- Несколько комнат суммируются; `total = subtotal × (1 + vat_pct/100)`.

## 6. Фактически реализованный REST API

| Метод и маршрут | Назначение |
|---|---|
| `POST /api/estimates` | создать смету |
| `GET /api/estimates/{id}` | получить смету |
| `PUT /api/estimates/{id}` | обновить базовые поля |
| `DELETE /api/estimates/{id}` | удалить смету |
| `POST /api/estimates/{id}/rooms` | добавить комнату с проёмами и работами |
| `PUT /api/rooms/{id}` | заменить данные комнаты |
| `DELETE /api/rooms/{id}` | удалить комнату |
| `POST /api/estimates/{id}/calculate` | пересчитать и сохранить итог |
| `POST /api/estimates/{id}/photos` | загрузить фото multipart |
| `DELETE /api/photos/{id}` | удалить фото и metadata |
| `GET /api/shared/{share_token}` | read-only данные по share-token |
| `GET /api/price-list` | read-only seed-прайс |

Ошибки возвращаются в конверте `{ "error": { "code", "message" } }`.

## 7. Вне scope (не делать)

Серверный PDF, экран/право редактирования прайс-листа, Alembic, HEIC,
markup_pct и status, правка норм расхода в форме, AI-анализ фото, авторизация,
Excel, мультивалютность. Полный список с причинами — §12 дизайн-дока.
